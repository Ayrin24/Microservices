## Задача 1: API Gateway

### Сравнительная таблица

| Критерий | Nginx (OSS) | Traefik | Kong Gateway (OSS) | HAProxy |

| Динамическая конфигурация | ⚠️ перезагрузка конфига (reload) | ✅ подхватывает изменения без перезапуска | ✅ через Admin API | ⚠️ reload / Runtime API |
| Расширяемость | модули, Lua (OpenResty) | middleware, плагины | богатая экосистема плагинов | Lua |

| Распространённость и документация | очень высокая | высокая | высокая | высокая |

### Выбор: Nginx

Все три обязательных требования закрываются в open-source версии без дополнительных компонентов:

- **Маршрутизация** — блоки `location` с `proxy_pass` на нужный сервис.
- **Аутентификация** — директива `auth_request` отправляет подзапрос в сервис авторизации (например, `GET /v1/token/validation`) и пропускает основной запрос только при ответе 2xx. Логика проверки остаётся в отдельном сервисе, а шлюз её не дублирует.
- **HTTPS** — терминация TLS на шлюзе, внутри сети сервисы могут работать по HTTP.

Дополнительные причины:

- минимальная сложность эксплуатации: один бинарник и один конфиг, который хранится в Git вместе с остальной инфраструктурой;
- высокая производительность и низкое потребление ресурсов;
- большое сообщество, легко найти специалистов и готовые решения;
- тот же Nginx можно использовать как балансировщик и раздавать статику, отдельный компонент не нужен.

Когда стоит перейти на другое решение: если сервисов станет много и потребуются управление через API, готовые плагины (rate limiting, OAuth2, аналитика) и самообслуживание для команд, лучшим вариантом будет **Kong**. Если нужна динамическая конфигурация в Kubernetes без перезагрузок, подойдёт **Traefik**.

## Задача 2: Брокер сообщений

### Сравнительная таблица

| Критерий | RabbitMQ | Apache Kafka | ActiveMQ Artemis | Redis Streams |
|---|---|---|---|---|
| Кластеризация для надёжности | ✅ кластер, quorum queues (Raft) | ✅ репликация партиций | ✅ кластер, live/backup | ⚠️ репликация и Sentinel/Cluster, при сбое возможна потеря данных |
| Хранение сообщений на диске | ✅ durable-очереди и persistent-сообщения | ✅ всегда, лог на диске | ✅ журнал (journal) | ⚠️ AOF/RDB, основное хранилище — память |
| Скорость | ✅ десятки тысяч сообщений/с на узел | ✅✅ самая высокая, сотни тысяч и более | ✅ средняя | ✅✅ высокая |
| Форматы сообщений | ✅ любой payload (байты), заголовки, content-type | ✅ байты, Avro/Protobuf/JSON через Schema Registry | ✅ любой payload | ✅ пары ключ-значение |
| Протоколы | AMQP 0-9-1 / 1.0, MQTT, STOMP | собственный протокол Kafka | AMQP, JMS, MQTT, STOMP | протокол Redis |
| Разделение прав по потокам | ✅ права configure/write/read по vhost и именам (regex) | ✅ ACL на топики | ✅ роли и права на адреса | ⚠️ ACL на команды и ключи |
| Простота эксплуатации | ✅✅ web-интерфейс, простая настройка | ⚠️ сложнее (партиции, ребалансировка, KRaft) | ✅ средняя | ✅ простая, но это не специализированный брокер |
| Модель | очереди, маршрутизация (exchanges) | распределённый лог, повторное чтение | очереди и топики (JMS) | лог в Redis |

### Выбор: RabbitMQ

Он закрывает все шесть требований с хорошим балансом:

1. **Кластеризация** — кластер из нескольких узлов и quorum queues на протоколе Raft: при потере узла очередь остаётся доступной без потери подтверждённых сообщений.
2. **Хранение на диске** — durable-очереди и persistent-сообщения сохраняются на диск до подтверждения (ack) получателем.
3. **Скорость** — для типичной микросервисной нагрузки (команды, события, фоновые задачи) производительности достаточно, задержки низкие.
4. **Форматы сообщений** — брокер не интерпретирует тело сообщения: можно передавать JSON, Protobuf, Avro и другие форматы, тип указывается в заголовках.
5. **Права доступа** — виртуальные хосты (vhost) изолируют сервисы друг от друга, а для каждого пользователя задаются права на конфигурирование, запись и чтение конкретных очередей и exchange.
6. **Простота эксплуатации** — готовый web-интерфейс управления, мониторинг через Prometheus, много документации и готовых Docker/Helm-решений.

Дополнительно: гибкая маршрутизация (direct, topic, fanout, headers exchanges), поддержка нескольких протоколов, зрелое решение.

Почему не остальные:

- **Kafka** быстрее, но сложнее в эксплуатации; она нужна, когда требуются потоки событий большого объёма, долгое хранение и повторное чтение истории.
- **ActiveMQ Artemis** подходит, если вокруг уже есть Java/JMS-экосистема; по скорости и удобству эксплуатации уступает RabbitMQ и Kafka.
- **Redis Streams** — не специализированный брокер: данные в основном хранятся в памяти, надёжность на диске слабее, права доступа грубее.

### Схема работы

| Запрос на шлюз | Проверка токена | Куда направляется |
|---|---|---|
| `POST /v1/register` | нет | security `POST /v1/user` |
| `POST /v1/token` (и `/token`) | нет | security `POST /v1/token` |
| `GET /v1/user` | да | security `GET /v1/user` |
| `POST /v1/upload` (и `/upload`) | да | uploader `POST /v1/upload` |
| `GET /v1/user/{image}` | да | minio `GET /images/{image}` |
| `GET /images/{image}` | нет | minio `GET /images/{image}` |

Проверка токена: шлюз делает подзапрос `GET /v1/token/validation` в сервис security с тем же заголовком `Authorization`. Если ответ 2xx, запрос пропускается дальше, иначе клиент получает ошибку от security (401/403).
